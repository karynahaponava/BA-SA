### 3.  Формирование MVP и бэклога. Написание User Story и Use Case.
*mvp*: приложение без онлайн-оплаты, акций, без курьеров на автомобилях, только пешие.

*backlog*:
[Высокий приоритет]: Разработать базу данных для хранения каталога напитков и еды, доставок и курьеров.
[Высокий приоритет]: Создать отдельный экран для планшета баристы, чтобы новые оплаченные заказы автоматически появлялись там со звуковым уведомлением.
[Средний приоритет]: Подключить платежный шлюз.
[Низкий приоритет]: Разработать логику применения промокодов и расчета скидок.
[Низкий приоритет]: Настроить автоматическую рассылку push-уведомлений клиентам о том, что курьер забрал заказ.

*user story*:
-  Как клиент, я хочу видеть статус заказа (готовится / передан курьеру), чтобы понимать, когда мне нужно выходить встретить курьера.
-  Как курьер, я хочу видеть точный номер подъезда, этаж и код домофона на главном экране заказа, чтобы не тратить время на звонки клиенту и быстрее отдавать заказы.
-  Как бариста, я хочу, чтобы заказы на доставку подсвечивались на моем экране красным цветом, чтобы я собирал их в первую очередь.

*use cases*:
Основной сценарий:
-  Клиент вводит свой адрес в текстовое поле и нажимает кнопку «Проверить».
-  Система рассчитывает расстояние и понимает, что адрес находится в 1 км от кофейни (входит в допустимую зону).
-  Система выводит на экран зеленую галочку, рассчитывает примерное время доставки и делает активной кнопку «Перейти к оплате».

Альтернативный сценарий (адрес вне зоны обслуживания):
-  Клиент вводит свой физический адрес и нажимает «Проверить».
-  Система определяет координаты и вычисляет, что адрес нарушает бизнес - правила.
-  Система блокирует кнопку оплаты и показывает на экране красное уведомление: «К сожалению, мы пока не доставляем по этому адресу. Вы можете заказать самовывоз».

### 3.  Построение системных диаграмм (UML) и помощь команде.

*А. UML Sequence Diagram (Диаграмма последовательности)*

Сценарий: Оплата заказа и передача его на кухню.
Участники: Мобильное приложение, Сервер кофейни, API Банка, База данных, Планшет баристы.

1.  Приложение отправляет на Сервер API-запрос `POST /pay` с суммой и ID заказа.
2.  Сервер обращается к API Банка с запросом на списание средств.
3.  API Банка возвращает ответ `200 OK`.
4.  Сервер отправляет запрос в Базу данных: `UPDATE order_status = 'Paid'`.
5.  Сервер параллельно отправляет Push-уведомление на Планшет баристы: «Поступил новый заказ №2».
6.  Сервер возвращает в приложение ответ об успехе, и Приложение показывает клиенту зеленый экран.

*Б. UML State Machine Diagram (Диаграмма состояний)*
Сущность «Заказ»
Цепочка состояний: `Created` (Создан в корзине) -> `Paid` (Оплачен клиентом) -> `Preparing` (Готовится баристой) -> `Delivering` (Передан курьеру) -> `Done` (Доставлен).

### 4.  Написание SRS.
*Функциональные требования (FR):*
-  Система должна скрывать из интерфейса приложения позиции из таблицы Меню, если статус_наличия = false.
-  Система должна вычислять расстояние от кофейни до клиента, передавая данные из поля координаты (таблица Пользователи) во внешний сервис карт.

*Нефункциональные требования (NFR):*
-  Время ответа сервера при нажатии кнопки «Проверить адрес» не должно превышать 2 секунд.
-  Приложение должно стабильно работать при пиковой нагрузке до 500 одновременных заказов в утренние часы.

*Проектирование контрактов API:*
GET /api/v1/menu — запрос на получение актуального каталога.
POST /api/v1/orders — отправка сформированной корзины на сервер.

### 5.  Анализ возможных отклонений (Обработка Edge Cases)

- Если API картографического сервиса недоступно (тайм-аут ответа более 5 секунд), система должна прервать запрос и показать UI-алерт: "Сервис проверки адреса временно недоступен. Пожалуйста, повторите попытку через минуту".

- Если курьер потерял сеть и нажал кнопку «Доставлено», мобильное приложение должно сохранить статус Done в локальном кэше телефона. Как только интернет появится, приложение должно автоматически отправить POST-запрос на сервер кофейни для обновления БД. 

- Если на 3-м шаге UML-диаграммы банк возвращает ошибку нехватки средств, система НЕ должна переводить заказ в статус Paid. Сервер должен вернуть клиента на экран корзины и показать сообщение об ошибке оплаты.
